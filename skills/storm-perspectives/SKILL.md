# 관점 탐색 (STORM 수강생판)

## 공용 경로

먼저 이 스킬 파일에서 상대 경로 `../../references/vault-layout.md`를 읽고, 대상 볼트의 `CLAUDE.md`와 함께 적용합니다. 아래 경로 예시는 공용 표의 역할을 뜻하며 사용자 규칙이 우선합니다.

Stanford의 STORM 방법을 Claude Code에서 가볍게 돌리는 스킬입니다. 원리는 하나입니다. **질문을 바로 던지면 얕고 한쪽으로 치우친 질문만 나옵니다.** STORM은 탐사 기자처럼 일합니다. 먼저 서로 다른 관점을 찾고, 관점마다 전문가를 인터뷰하고, 모든 주장을 다시 찾아볼 수 있는 출처에 묶습니다.

연구에서는 **관점끼리 부딪치는 지점이 연구 갭 후보**가 됩니다. 이 스킬의 최종 산출물도 그 후보 목록입니다.

## 언제 쓰는가

- **씁니다:** 연구 질문을 고르기 전, 한 주제에 어떤 쟁점이 있는지 보고 싶을 때. 여러 분야가 겹치는 주제. 내 주장이 한쪽 관점에만 기대고 있는지 점검할 때.
- **쓰지 않습니다:** 논문을 넓게 모으는 문헌 조사(`research-search`), 사실 하나 확인(웹 검색), 내 위키에 이미 정리된 내용 묻기.

## 모드

| 모드 | 관점 수 | 진행 | 사용량 | 누가 |
|---|---|---|---|---|
| **Light (기본값)** | 3~4개 | 메인 대화가 관점을 하나씩 차례로 맡아 인터뷰 | 보통 | 수강생 |
| Full | 6~8개 | 관점마다 서브에이전트를 동시에 띄움 | **큼** | 강사 시연용 |

사용자가 Full을 직접 요청하지 않으면 **항상 Light로 진행합니다.** Full은 Claude Pro 한 계정의 사용량을 빠르게 씁니다. 사용자가 Full을 요청하면 사용량이 크다는 점을 먼저 알리고 한 번 더 확인합니다.

## 실행 전 정하기

아래를 한 번에 묻고 확인받습니다. 사용자가 이미 말한 것은 다시 묻지 않습니다.

1. **주제:** 한두 문장. 연구 검색 리포트가 있으면 그 경로를 받아 먼저 읽습니다.
2. **관점 수:** 기본 3개. 주제가 넓으면 4개.
3. **저장 위치:** 사용자가 정한 폴더. 없으면 `Research/` 아래에 저장하고, `Research/` 안에 연구 프로젝트 폴더가 하나뿐이면 그 폴더에 저장합니다. 파일 이름은 `YYYY-MM-DD 관점 탐색 - 주제.md`입니다.

볼트 맨 위에 `CLAUDE.md`가 있으면 먼저 읽고, 적힌 폴더 이름과 규칙을 따릅니다.

## 1단계: 관점 찾기

주제에 필요한, 서로 진짜로 다른 관점 3~4개를 정합니다. 관점마다 아래를 씁니다.

```text
관점 [N]: [이름. 예: 교육공학 연구자, 현장 교사, 정책 입안자, 회의론자]
- 중요하게 보는 것: 2~3문장
- 가장 날카로운 질문: 3개
- 이 관점이 필요한 이유: 1문장
- 출발 편향: 이 관점이 처음부터 의심하는 것, 당연하게 여기는 것
```

조건:

- 말만 다르고 같은 각도인 관점은 안 됩니다. 결론이 실제로 갈릴 수 있어야 합니다.
- 최소 1개는 **회의론자나 반대 관점**입니다.
- 최소 1개는 **현장 실무자 관점**입니다.
- **출발 편향**을 꼭 적습니다. 같은 AI가 모든 관점을 맡기 때문에, 출발점을 일부러 다르게 정해야 관점이 실제로 갈립니다.

**사용자(연구자) 확인:** 관점 목록을 보여 주고 확인받습니다. 사용자는 빼거나, 더하거나, 고칠 수 있습니다. "좋아요", "진행" 같은 답을 받기 전에는 다음 단계로 가지 않습니다.

## 2단계: 관점별 인터뷰 (Light 모드)

메인 대화가 관점을 **하나씩 차례로** 맡습니다. 한 관점에서 인터뷰어와 전문가를 함께 맡아 3턴 안팎으로 진행합니다.

### 찾는 순서 (관점마다)

1. **내 볼트 먼저:** `CLAUDE.md`의 규칙을 따르고, 위키의 `INDEX.md`, `Literature/`, `Topic/`, `Research/`에서 핵심 개념을 Grep으로 찾습니다. 내가 이미 정리한 것을 다시 조사하지 않기 위해서입니다.
2. **내 Zotero 서재:** Zotero 앱이 켜져 있으면 `zotero_search_items(query="<검색어>", qmode="everything", limit=5)`로 찾습니다. `zotero_semantic_search`가 있고 색인이 만들어져 있으면 그것을 먼저 써도 됩니다. 읽기만 합니다.
3. **웹:** 관점의 질문을 WebSearch로 찾고, 고른 페이지를 WebFetch로 엽니다. 검색어는 주제어 나열보다 "연구는 X에 대해 무엇이라고 말하는가", "X가 실패한 사례", "X 비판"처럼 만듭니다.

사용량을 아끼기 위해 **관점마다 웹 검색은 2~3번, 열어 보는 페이지는 3개 안팎**으로 합니다.

### 인터뷰 진행

인터뷰어가 관점의 날카로운 질문을 던지고, 전문가가 찾은 출처로 답하고, 인터뷰어가 그 답의 약한 부분을 다시 묻습니다. 쉽게 동의하고 넘어가지 않습니다.

**원칙:** 출처로 뒷받침하지 못하는 주장은 `[근거 없음]`으로 표시합니다. 출처를 지어내지 않습니다. URL은 실제로 열어 본 것만 적습니다.

### 관점별 기록

관점 하나가 끝날 때마다 아래 형식으로 짧게 정리해 두고 다음 관점으로 넘어갑니다. 앞 관점의 결론에 끌려가지 않도록, 다음 관점을 시작할 때는 그 관점의 출발 편향을 다시 읽고 시작합니다.

```text
### 관점 N: <이름>
- Q1 / A1 (출처: URL 또는 볼트 경로)
- Q2 / A2
- Q3 / A3
- 핵심 발견 3개
- 근거 없음 목록
- 다른 관점과 부딪칠 것 같은 지점
```

## 3단계: 합의점과 충돌 지점 나누기

모든 관점 기록을 모아 **합의점**과 **충돌 지점**을 따로 적습니다. 충돌은 숨기지 않습니다.

충돌 지점마다 아래를 적습니다. 이것이 연구 갭 후보입니다.

```text
충돌 [N]: <한 줄 요약>
- 관점 A의 주장과 근거 [n]
- 관점 B의 주장과 근거 [m]
- 왜 갈리는가: 데이터가 다름 / 정의가 다름 / 맥락(분야, 나라, 대상)이 다름 / 아직 연구가 없음
- 연구 갭 후보: 이 충돌을 풀려면 어떤 연구가 필요한가
```

충돌 지점이 거의 없으면 관점이 충분히 다르지 않다는 뜻입니다. 사용자에게 그렇게 말하고, 1단계로 돌아가 출발 편향을 더 다르게 잡을지 묻습니다. "다양한 관점을 봤다"고 꾸미지 않습니다.

## 4단계: 사용자(연구자) 확인

**가장 중요한 단계입니다.** 같은 AI가 모든 관점을 맡았기 때문에, 이 파이프라인 안에서 진짜로 다른 시각은 연구자 한 사람뿐입니다.

합의점과 충돌 지점을 보여 주고 묻습니다.

- "조사 결과는 이렇게 말합니다. 연구자님의 경험이나 분야 지식으로 볼 때 맞습니까?"
- "빠진 관점이나 틀린 내용이 있습니까?"
- "연구 갭 후보 중 더 파 보고 싶은 것은 무엇입니까?"

사용자가 고치거나 더한 내용은 "연구자 의견"으로 구분해 기록합니다. 출처로도 연구자 의견으로도 확인되지 않은 주장은 `[근거 없음]`으로 둡니다.

## 5단계: 정리하고 쓰기

확인받은 내용만으로 결과 문서를 씁니다. 2단계에서 찾지 않은 새 정보를 이 단계에서 끌어오지 않습니다. 자료가 얇은 부분은 일반론으로 채우지 않고 "더 조사 필요"라고 씁니다.

```markdown
---
title: "<주제> — 관점 탐색"
date: YYYY-MM-DD
type: perspective-map
mode: light
perspectives: 3
tags:
  - research
  - research-gap
---

# <주제> — 관점 탐색

## 요약
3~5줄. 가장 중요한 충돌 지점 하나를 포함합니다.

## 관점
관점별 이름, 중요하게 보는 것, 출발 편향, 핵심 발견

## 합의점

## 충돌 지점과 연구 갭 후보
3단계 형식 그대로

## 연구자 의견
4단계에서 받은 내용

## 아직 풀리지 않은 질문

## 근거 없음 목록

## 참고문헌
[1] 저자, 제목, 연도, URL 또는 볼트 경로 — web / paper / zotero / vault
```

## 6단계: 점검

저장하기 전에 직접 점검합니다.

1. **한 출처에 기대기:** 한쪽으로 치우친 출처 하나에 너무 많이 기대고 있지 않습니까?
2. **억지 연결:** 이어지면 안 되는 사실을 이어 붙이지 않았습니까?
3. **빠진 관점:** 아무도 던지지 않은 질문은 무엇입니까?
4. **남은 모순:** 3단계의 충돌 중 정리되지 않은 것이 있습니까?
5. **근거 없는 주장:** 본문에 `[근거 없음]` 주장이 확인된 것처럼 섞여 있지 않습니까?

점검 결과를 사용자에게 보여 주고, 고칠 방향을 확인받은 뒤 저장합니다. 저장한 뒤 경로를 알려 주고, 다음 단계로 연구 갭 후보 중 하나를 골라 `research-search`로 더 찾거나 연구 질문으로 다듬는 일을 제안합니다. 연구 질문을 고르는 것은 연구자입니다.

## Full 모드 (강사 시연용, 사용량 큼)

사용자가 Full을 직접 요청하고 사용량 안내에 동의했을 때만 씁니다.

- 관점 6~8개를 정하고, 1단계 확인을 받은 뒤 관점마다 서브에이전트를 **한 메시지 안에서 동시에** 띄웁니다.
- 서브에이전트는 위의 "찾는 순서"와 "인터뷰 진행"을 그대로 따르고, 결과를 `Research/storm-<YYYYMMDD-HHMM>/pov-NN-<이름>.md` 파일로 직접 씁니다. 대화에는 200단어 이내 요약, 파일 경로, 근거 없음 개수만 돌려줍니다. 인터뷰 전문이 메인 대화로 쏟아지면 뒤 단계를 진행할 여유가 없어지기 때문입니다.
- 3단계부터는 메인 대화가 파일을 읽어 Light 모드와 같은 순서로 진행합니다. 6단계 점검은 메인 대화가 직접 합니다.

## 다양성에 대해 솔직하게

원래 STORM 응용판은 서로 다른 AI 모델 여러 개를 관점마다 돌려 맹점을 다르게 만들었습니다. 이 스킬은 한 모델이 모든 관점을 맡으므로 **그 장점은 없습니다.** 같은 모델은 같은 맹점을 가집니다.

남아 있는 다양성은 세 가지입니다.

1. **출발 편향:** 1단계에서 관점마다 출발점을 다르게 심습니다.
2. **다른 검색:** 관점마다 다른 검색어로 다른 출처를 만납니다.
3. **연구자:** 4단계의 사용자 확인이 유일하게 진짜로 다른 시각입니다.

결과가 한쪽으로 모인다고 느껴지면 사용자에게 그렇게 말합니다.

## 알려진 실패 유형

1. **한 출처에 기대기:** 치우친 출처 하나에 결론이 끌려갑니다.
2. **억지 연결:** 관계없는 사실을 이어 붙입니다.
3. **같은 결론으로 모이기:** 관점 이름만 다르고 결론이 같아집니다. 3단계의 충돌 지점이 비어 있으면 이 증상입니다.

1과 2는 Co-STORM 논문이 밝힌 실패 유형이고, 3은 한 모델로 돌리는 이 스킬에서 생기는 문제입니다.
